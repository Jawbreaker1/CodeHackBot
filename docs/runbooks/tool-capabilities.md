# Model tool capabilities

BirdHackBot has three distinct model roles. A tool shown to one role is not automatically callable by another. The prompt catalog in `internal/behavior/frame.go` describes this division to every model; the role-specific prompt supplies the exact JSON contract.

When the operator asks for tools, the coordinator should name the harness operations below. Installed Kali programs are examples of what a worker can invoke through `bash`, not additional built-in model tools.

The configured Qwen profile requests JSON-schema object output for structured control decisions. Ordinary chat replies remain text. This is a provider setting in `config/model-profiles.local.json` (`structured_json: true`), not a parser that guesses meaning from prose.

| Phase | Harness-defined choices | What they can do |
| --- | --- | --- |
| Intake conversation | `list_directory(path)`, `host_system()`, `local_network()` | With approval, list workspace entry names/types, read fixed host identity, or read local interface/route/neighbor metadata. No arbitrary file reads, commands, probes, or changes in this phase. Intake can also return a goal/scope **proposal** for operator review. |
| Assessment coordinator | Plan worker tasks, revise the plan, converse with the operator | The coordinator does not execute commands. It delegates scoped outcomes to workers after plan review. |
| Assessment worker | `bash`, `load_strategy`, `update_plan`, `ask_user`, `step_complete`, `blocked` | `bash` runs one direct executable with literal arguments or one explicit Bash script, subject to the session's approval policy. It handles scoped inspection, testing, and file operations without separate command-specific tools. `load_strategy` loads one bounded local guide into worker context. The remaining choices update the plan, ask a question, finish with evidence, or report a blocker. |

`bash` can call verified installed Kali and host tools for source review, local file work, scanning, advisory research, or browser automation. Nmap, Metasploit, SearchSploit, John, Hashcat, curl, and Playwright are **not separate built-in model tools**; a worker must verify the relevant binary, package, module, or database before using it. Connected-mode web retrieval must obey scope. Air-gapped mode uses only local resources. A small task-local helper may be built when existing tools are insufficient, with its creation and execution logged as separate commands. Prefer a short shell script for command composition, Python with its standard library for substantial parsing or transformations, and JavaScript for the existing [Playwright runner](../../tools/playwright-runner/README.md). Declare helper source and validation output as worker artifacts. Those files remain in that assessment's task workspace; another worker can reuse an exact recorded artifact after inspecting its source, verifying its applicability, and obtaining the normal execution approval. Nothing is implicitly promoted across customer sessions.

Report generation belongs to the assessment runtime: it renders the coordinator's structured findings and worker evidence into `report.md` under the assessment session folder. It does not run through `bash` or require the model to invent an output path. The web transcript links to the finished report and analysis view; the customer analysis view links to its unified Markdown report. The [reporting strategy](../strategies/evidence-reporting/SKILL.md) describes the expected executive and technical sections. The saved report is a draft for professional review.

The default session policy asks for approval of every execution. The operator can choose another policy in session settings. When the operator asks to approve each file change, keep that mode at **Approve every execution** and use a separate `bash` invocation for each item. Approval exposes the exact invocation; it does not expand scope. The current runtime relies on the authorized VM and operator review rather than an OS-level filesystem sandbox or network allowlist.
