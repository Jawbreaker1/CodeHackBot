# Browser data-flow investigation

Use this guide for a concrete cross-component question, not as a reason to capture every request or read every script.

1. Name the value or decision to trace, its source, the expected trust boundary, and the observable result that would confirm or refute the concern. If a workflow has multiple sensitive values, distinguish them by where they originate and how long they live before selecting the most consequential path; evidence about one does not settle another. Prefer a synthetic marker over a real token or customer datum. Record the tested role, page, and browser state.
2. Follow the relevant path across the initial HTML, script loading order, URL and redirect handling, DOM, storage or cookies, API responses, and outgoing requests. Inspect only the components needed to explain that path. Trace a value from its source through transformations to a specific sink; seeing a source and a destination in the same bundle is only a lead. Compare observations from separate source, browser, and network workers before closing a path. Distinguish client-side visibility from server-side authorization and code that could run from code that actually ran.
3. Use bounded browser captures and attributable source excerpts together. Inspect the runner's redacted `browser-network.json` for off-origin requests, URL shape, and the observed `navigator.webdriver` signal. If a page may behave differently under automation, do not use an absent Playwright request as proof that an ordinary visitor sends none. Preserve the exact origin, request destination, method, relevant URL or body fields, timing, and response status only in restricted evidence needed for the question. External services are separate destinations: observe ordinary in-scope page behavior without actively probing an out-of-scope service. Keep sensitive values out of ordinary logs and reports.
4. Test the smallest plausible hypothesis with controlled state. Compare a positive and negative control when practical, such as before and after a user action, with and without a synthetic marker, or across two authorized roles. An offline browser fixture can test a suspected client-side path without sending a marker to a real third party; it establishes that code path under those conditions, not a live disclosure. Account for reloads, stale storage, caches, redirects, and browser policy before attributing an effect to the application.
5. Hand the coordinator a short chain of observed steps with exact evidence references, the missing link if any, and one bounded next check. A script reference, storage setting, or third-party request alone does not prove disclosure or exploitability. Report a confirmed finding only when the relevant value reached the unintended boundary under the tested conditions.

Use `web-application` for a broad site assessment and `identity-access` when the main question is an account or authorization boundary. This guide narrows the investigation to one browser-mediated data flow; it does not expand scope or approve target contact.
