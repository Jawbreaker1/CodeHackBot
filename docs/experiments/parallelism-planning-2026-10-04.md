# Coordinator worker-count planning check

The blind webhook GUI review succeeded but assigned two first-round workers that read the same four files and tested the same signature-to-state path. This check isolates the coordinator's initial task split without executing tools or contacting a target. It uses the production coordinator behavior frame and Daybreak Blue at high reasoning, with synthetic local directory paths. The operator approved six direct subscription-backed model calls.

The first candidate instruction said to choose separate testable outcomes rather than different labels for one evidence path. Three identical planning calls scoped to the single, uncharacterized `client-flow-lab/build-a` application each proposed **two** workers. Their nominal topics differed (input flow versus configuration or sensitive data), but the actual build has one 30-line JavaScript module and a small HTML entry page. The split was based on possible issue categories, not observed independent surfaces, so it risks repeating the same source trace. The live evaluation correctly failed its one-worker expectation in all three attempts.

Three identical calls scoped to **two explicitly independent applications**, `client-flow-lab/build-a` and `webhook-lab`, each proposed one worker per application. The tasks were separate and independently useful, and the live evaluation passed that case in all three attempts.

The instruction was then refined: for one uncharacterized target, prefer one bounded first worker to discover its real structure and test the strongest material path; split immediately when operator input or recorded evidence already establishes independent targets or questions. This remains model guidance, not a runtime worker-count rule. It preserves later parallel work and independent validation.

The operator approved a second set of six direct planning calls. With the refined instruction, **3/3** calls for the single uncharacterized application assigned **one** worker, and **3/3** calls for the two independent applications assigned **two**, one per application. Every returned plan passed the coordinator's structured decision validator. The narrow plans explicitly prioritized the observed input-to-effect path before any later split. No workers or tools ran during either planning check. This shows a repeatable improvement in the *initial plan choice* for these two fixtures, not a measured reduction in end-to-end time, model calls, missed findings, or false positives. A later [same-prompt GUI run](webhook-efficiency-2026-10-04.md) also chose one initial worker, but took longer overall because it pursued an additional replay lead. An unseen larger target is still needed to evaluate discovery and end-to-end efficiency.
