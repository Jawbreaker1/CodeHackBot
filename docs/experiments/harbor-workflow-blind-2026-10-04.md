# Blind two-role editorial workflow assessment

This is one Daybreak Blue GUI smoke test of an unfamiliar local web/API/source workflow. It is not an acceptance rate, a direct Codex comparison, or evidence that BirdHackBot will find the same class of issue in arbitrary applications.

The synthetic Harbor editorial desk is in `testdata/review-workflow-lab/`. Before the assessment, `python3 scripts/check_review_workflow_lab.py` passed two loopback tests: the current app can publish a post-approval edit, while a separate fixed-control handler rejects the same edit at publication. The source SHA-256 was `76881c40bb2f6ce9dce0c1f31fe5b92ba07d3b449ae79bd4b7df088c9efc46fc` before and after the run. The fixture has two roles, browser forms, JSON read routes, and one fabricated notice. It resets on server restart. The oracle script was outside the source directory named in the operator prompt; the prompt did not disclose the flaw or the fixed control.

The operator used the existing BirdHackBot GUI at `http://127.0.0.1:8123/`, selected the **Focused** depth, kept per-execution approval, and used `gpt-daybreak-blue-latest` at high reasoning. The neutral prompt named only the local target `http://127.0.0.1:8766/`, the source/demo-account directory, permission for bounded two-role browser or HTTP tests on the fabricated notice, and a request for independent validation and an evidence-backed report. No external host, package install, or source modification was allowed. The assessment is `sessions/web/harbor-workflow-blind-20261004/web-assessment-20261004-175245.834838878-000002/`.

The coordinator selected one initial worker to map the source and running workflow. That worker independently identified the approval-to-publication boundary, recorded negative role controls, and observed reviewer approval of revision 2 followed by anonymous publication of the author's unreviewed revision 3. The coordinator described this as provisional and assigned a later worker for a separate challenge. The verifier used new client sessions and a new marker: revision 5 was approved, revision 6 was published without renewed review, and anonymous output matched revision 6 rather than revision 5. The coordinator promoted one high-severity finding to **reproduced** and produced a report and Analysis entry with the remedy. No extra finding was invented. Seven report evidence paths resolve to saved local files, and both HTTP transcripts omit the synthetic passwords.

The run took **14 minutes 51 seconds** (17:52:45–18:07:37 UTC), with **22 model calls**, **0 failed model calls**, **364,973 provider-reported tokens**, **2 completed workers**, and **3 accepted coordinator decisions**. The final coordinator request was 69.8 KiB on disk, and the last worker requests were 90.8 KiB and 104.5 KiB. The selected worker packets retained the exact target and source boundary, current revision evidence, and transcript references. The final worker packet's largest sections were recent results (~29 KiB), behavior frame (~13.7 KiB), retrieved memory (~13 KiB), and plan history (~10.6 KiB); context had not yet been compacted. The app's input ceiling was 128 KiB. These sizes are useful efficiency signals, not provider token-window measurements.

Two generic weaknesses are visible in the trace. First, the coordinator attempted to close a lead ID that had never been opened; the validator rejected that decision and a correction succeeded. A similar correction occurred in the earlier client-flow assessment, so this is a recurring planning-contract cost rather than a Harbor-specific behavior. Second, the verifier spent two additional decisions repairing its own over-strict helper-source check and wrong transcript-record-count expectation. The recorded outcome remained correct, but this illustrates disproportionate bookkeeping during a small test.

The report also **overstates one control**. It says the verifier showed an “ordinary unapproved revision” was rejected with HTTP 409. Its transcript shows that this request was made after an edit while the notice was still in the `published` state inherited from the first worker's run. The rejection is real, and the first worker separately recorded a pre-approval rejection from the initial draft state, but the verifier's 409 does not by itself establish the described pre-state. This wording should be corrected before using the draft as a formal customer report. The core finding is independently supported by the approved/current/public revision comparison.

The next capability gate should use at least two further *unlike*, frozen fixtures with larger code and browser workflows, including a fixed target where the tempting hypothesis is false. Score target-side detection, false findings and overclaimed controls, evidence validity, time and model calls, and the exact information retained in worker/coordinator packets. A truly blind Codex comparison must use a fresh context with matched target access, model, time, and approval conditions; the author of this fixture cannot serve as its blind comparator. Production logic should change only when a generic bottleneck is reproduced, and no Harbor-specific rule should be added.
