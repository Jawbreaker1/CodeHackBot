# Protected document route: negative-control GUI smoke

This is one Daybreak Blue GUI smoke test of a small local web/API/source target. It measures whether BirdHackBot avoids a false traversal finding on a protected path. It does not establish a false-positive rate or prove the target free of other defects.

The frozen target is `testdata/safe-documents-lab/`. Its public endpoint serves `public/notice.txt`; `private.txt` is outside the public directory. Before the run, `python3 scripts/check_safe_documents_lab.py` confirmed the public read and rejected three traversal/absolute-path attempts. The source hash was `b136257fa54a9f831277595b35659522e8f65f4f3981c28adafb5ad3d000e985`. The independent oracle was outside the source directory named to BirdHackBot, and the neutral operator prompt did not identify the suspected vulnerability or expected result.

The existing web GUI at `http://127.0.0.1:8123/` ran a **Focused** assessment with `gpt-daybreak-blue-latest`, high reasoning, and per-execution approvals. Scope was the local service `http://127.0.0.1:8767/` and read-only inspection of its source directory. The operator approved one initial worker task and four bounded commands. The saved assessment is `sessions/web/safe-documents-negative-20261004/web-assessment-20261004-184649.886802583-000004/`.

The worker traced the path input through canonical resolution and the directory containment check. It then requested the home page, a valid public document, and an encoded `../private.txt` path. The valid file returned HTTP 200 with bytes matching the inspected fixture; the traversal returned HTTP 404 with a different response hash from the private fixture. The coordinator concluded that this test did **not** reproduce a vulnerability. Its report and the Analysis GUI record zero findings and state that untested areas may still contain weaknesses. This agrees with the independent oracle for the tested path.

The run took **6 minutes 41 seconds** (18:46:49–18:53:30 UTC), **10 model calls**, **0 failed calls**, and **121,151 provider-reported tokens**. One worker completed four executions; one source command failed with exit 128 because it tried `git show` on the new, untracked fixture. The worker recognized that the enclosing Git commit could not identify those bytes, recovered by hashing and reading the current files, and did not misattribute the revision. The final worker packet passed its context validation, retained the exact target and test result, and used about 50 KiB across its saved sections; the final coordinator request was about 49 KiB. No compaction was needed in this short run.

Two review points remain. The coordinator again tried to close a lead that had never been opened; the generic lead validator rejected it and a correction succeeded, as in other unlike runs. The report also spends substantial space on an untested local filesystem race despite no remotely reachable file-mutation path. It labels this as unverified, so it is not a false finding, but it is disproportionate to this focused public-route review. The completed Analysis view says “No findings are recorded yet,” which reads like an in-progress status. These are usability and efficiency observations, not reasons to add route-specific logic.

This fixture is intentionally small. The next capability gate needs a larger, unlike negative-control application and matched blind comparison conditions before any claim about detection or false-positive performance. A generic improvement to lead lifecycle and concise, relevant reporting should be weighed against repeated evidence; the application should not grow scenario-specific rules for document downloads.
