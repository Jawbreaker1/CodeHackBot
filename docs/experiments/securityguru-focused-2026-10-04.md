# Focused SecurityGuru web assessment

On 2026-10-04, BirdHackBot ran a new GUI assessment of the exact hostname `securityguru.se` with `gpt-daybreak-blue-latest`. The ordinary operator prompt asked for a simple, low-volume, non-intrusive review of public pages, HTTP behavior, and available client code. It excluded credentials, state-changing forms, exploitation, brute force, high-volume scans, and testing embedded third-party hosts. The session is `sessions/web/securityguru/web-assessment-20261004-102409.741748602-000002/`.

The first pass took about 24 minutes and 38 model calls. The coordinator used two parallel baseline workers, then separate public-content, route-boundary, and unauthenticated-API workers. Chromium received a Cloudflare 403, but bounded HTTP requests obtained the homepage, dashboard shell, and one directly referenced JavaScript bundle. The sampled identity, order, scan-diff, and schedule API reads returned HTTP 401 without credentials. The report recorded one low-severity CSP candidate and no reproduced vulnerability. These observations do not establish that the site is free of more serious flaws.

The saved artifacts reveal a material question the first pass omitted. The dashboard bundle reads a `token` URL parameter in its verification component and sends that value to `/api/v1/auth/verify`; it also stores the returned bearer token in `localStorage`. The saved dashboard HTML loads an external analytics script and starts Matomo page-view tracking. The assessment did **not** establish that the verification route serves that same HTML, that a real token was transmitted to analytics, or that a 24-hour JWT is actually issued. No real token was collected or used. A harmless marker on an operator-controlled account and a captured browser request would be needed before calling the alleged magic-link leak reproduced.

A generic follow-up in the same session asked the coordinator to review existing client code and worker evidence for omitted trust boundaries without naming the suspected leak. The coordinator proposed two artifact-only workers, but its first two proposals failed lead-register validation. Correction prompts had returned only the first 4 KiB of a rejected decision, hiding its new leads near the end. The correction path now supplies prior accepted lead IDs and the rejected lead proposals explicitly; a regression test and full CI pass. The resumed GUI run then accepted the plan and preserved the new leads.

The additional bundle worker mapped many APIs and token storage but explicitly left `/auth/verify` semantics aside and never connected the URL token to analytics. The other worker's proposed exhaustive reread of every saved log and artifact was declined as disproportionate to this focused scan; its partial review adds no claim of complete coverage. The final session has seven accepted plans, 63 model calls, 1,230,995 reported tokens, no reproduced finding, one low-severity CSP candidate, and several unverified leads. It still does not name the possible URL-token/analytics path. The miss predates that declined reread: the relevant HTML and bundle were already saved and available to the first-pass worker and coordinator.

A later packet inspection found a more specific loss. The route-boundary worker's saved 46 KiB source-search output contained `new URLSearchParams(window.location.search).get("token")` and the `/api/v1/auth/verify` call around byte 17 KiB. The work API passed only an unconditional 8 KiB head preview into `output_evidence`; none of that worker's captured model packets contained `URLSearchParams`. The worker did see the page-shell Matomo observation and an isolated `/auth/verify` path, but not the control-flow excerpt needed to connect them. The executor preview now retains up to 64 KiB of medium output; the existing model-view budget decides when older observations must be shortened, and a regression test checks that an observation beyond the former 8 KiB boundary reaches the worker packet. This improves this concrete handoff loss but does not by itself guarantee a worker will recognize or validate a security path in a larger artifact.

This is a negative capability result. The primary problems were a lost middle-of-output observation, narrow then overbroad task assignments, and failure to synthesize the remaining cross-surface clues. The source-review and web-application guides now ask workers to follow material data and control flows across components and hand off unresolved paths. They deliberately do not prescribe the URL-token/telemetry scenario as a fixed checklist. An unlike, blind local A/B fixture succeeded at source-only detection, but the preview change has **not** yet been validated in a fresh real-model assessment. Acceptance should include larger unlike fixtures and a bounded target-side check with a harmless marker; compare missed and false leads, time, and model-call cost before claiming reliable discovery.
