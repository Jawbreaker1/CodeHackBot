# Blind webhook review through the web UI

This run checked whether BirdHackBot could find and verify a material flaw in a new, small source tree without being told the flaw or a preferred test. The target was an isolated Python webhook gateway under `testdata/webhook-lab/`. It is unrelated to the earlier URL-token, browser telemetry, ZIP, and cross-tenant exercises. The fixture was checked independently before the run, but the user prompt contained only its path, permission to read that directory and run bounded in-process tests with fabricated data, and a request for evidence-backed findings and controls.

The run used `gpt-daybreak-blue-latest` through the web GUI with the **Focused** depth. Session: `webhook-heldout-20261004 / web-assessment-20261004-132134.205026819-000002`. The coordinator chose two parallel first-round tasks: one traced signature verification, and the other traced handler effects. Both read the four source files and independently tested the same short-signature candidate. Their tests used synthetic secrets and payloads, a fresh in-memory ledger per call, missing and incorrect signature controls, valid full-signature controls, and the billing route as a comparison. Each found that one of 16 single-hex-character guesses was accepted by the delivery route and changed the ledger to `delivered`, while the billing route rejected a correct short prefix.

The coordinator initially tried to mark the finding reproduced from those two workers in the same round. The generic finding validator rejected that conclusion because no later-round validation task had completed. The coordinator then proposed a fresh independent challenge; the operator selected it in the GUI. That worker reproduced the effect with new fabricated inputs, including negative and positive controls. The final report recorded one **high** finding, described the affected trust boundary and impact, recommended full-length HMAC verification, and limited its claim to the in-process handler behavior. The web analysis view displayed the finding, priority, remedy, and independent challenge correctly. No source file was changed and no network contact or server startup was requested.

The session completed in **9 minutes 40 seconds** (13:21:34–13:31:14 UTC), using **18 model calls** and **226,678 reported tokens**, with no failed calls. The coordinator's last saved request used 64.4 KiB of the application's 128 KiB input ceiling. This is a successful generalization check, not a reliability estimate. It also exposes a cost and latency concern: a roughly 70-line local program needed nearly ten minutes and three workers. The first two workers converged on the same candidate rather than testing disjoint hypotheses, and the later-round validation policy added another worker. That additional check caught an invalid early claim of reproduction and gave a stronger result, so any speed improvement should preserve its evidentiary value.

The report and raw logs are stored in the session directory. The result supports the generic source-tracing and evidence-continuity changes; it does not justify adding a webhook-specific branch or prompt rule. Larger unseen codebases, multiple competing flaws, and false-positive controls remain untested.
