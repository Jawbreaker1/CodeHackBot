# Core logic validation — 2026-09-27

This is an implementation and user-path audit, not acceptance of BirdHackBot as a customer-ready penetration-testing platform. It separates deterministic contracts, one fresh real-model browser run, and unproven product claims. No target network was contacted and no repository file was changed by the browser assessment.

## Material findings

1. **High priority — dangerous-only approval can be bypassed by a wrong model risk label.** `internal/workerloop/execution.go` constructs the approval request from the worker response, including `Risk`. `internal/approval/policy.go` treats exact `low` plus three nonblank descriptive fields as enough to skip review; it does not examine the executable, arguments, shell, script, or effects. `internal/webapp/server.go` then grants session approval without prompting. The existing test confirms this policy for a generic low-risk request; the browser run traced the path but did **not** execute a harmless marker through it. This is a code-supported policy defect with an unverified end-to-end execution consequence. The mode's current label promises more than the implementation independently establishes. A correction should use a trusted execution-boundary decision or ask on uncertainty, with benign fixtures representing risky semantics; it should not depend on brittle command regular expressions.

2. **High priority — final report misstates the denied action.** The browser report says the operator declined “the final harmless validation action” and implies the marker test was denied. The actual approval audit records a redundant read of `permissions.go`, `server.go`, and related tests. The worker never proposed the marker command before it was stopped. Analysis repeats the report's incorrect explanation. The candidate/reproduced gate prevented an overclaim of a validated vulnerability, but the provenance narrative still became false. Report generation should distinguish the exact declined action from the unperformed objective and check important limitation statements against action logs.

3. **Medium priority — the shared model budget is not a concurrency limit.** `internal/assessment/meter.go` reserves a call, increments `inFlight`, and checks only total calls. The coordinator may launch two workers in parallel, while `internal/webapp/server.go` can answer an operator message on the same budget during the run. Three inference requests can therefore be in flight for one assessment, despite `docs/architecture.md` stating at most two concurrent requests. The current concurrency test uses a *total budget of two* and only shows that a third request exhausts that budget; it does not test a two-slot semaphore with a larger call budget. This matters for the local Qwen configuration with two concurrent slots. Add a shared concurrency gate and a test that holds two provider requests open while a third waits or is rejected predictably.

4. **Medium priority — handoff and context cost remain high.** In this small source-review task, the first worker's saved pre-LLM packet grew from about 18 KiB to 55 KiB over nine steps; the second worker started at 27 KiB and reached 50 KiB after five steps. The second worker reread much of the same source instead of using the first worker's cited logs to attempt its narrow validation. `internal/context/model_view.go` explicitly performs byte-bounded projection and truncation, not semantic summarization. The recent archive timing audit likewise found late 40–67 KiB worker prompts and duplicated helper discovery. The fresh run took about 11 minutes and 239k reported tokens for an approval-policy review, with the behavioral test still undone. Separate packets prevent cross-role contamination, but they do not yet provide economical, reliable long-session memory or evidence reuse.

5. **Open product gate — resume and isolation.** The web session store marks interrupted runs, and the coordinator can resume saved state, but `docs/architecture.md` explicitly defers exactly-once recovery of external effects and remote web authentication. The runtime does not enforce a network target allowlist or filesystem sandbox; air-gapped operation is an architectural requirement, not a demonstrated complete deployment. These are stated limitations, not new regressions discovered by this run. They require dedicated acceptance before customer use.

## Performance and strategy context

The separate archive timing record is important because it refutes a simple “missing skill” explanation. In the unsuccessful long run, all six workers loaded the relevant guide; only about 190 seconds were command execution within a 57.6-minute stopped session. The later focused run reduced time to the first target candidate test from about 22 minutes 46 seconds to 5 minutes 50 seconds, but it used a different rule family from an earlier successful run and did not recover the archive. The changes improved one timing metric; they have not established a reliable or superior generic strategy. The same unnecessary source rereading appeared in this unrelated approval-policy assessment, so handoff and decision-loop economy are plausible cross-task problems. Do not optimize the core around the archive fixture alone.

## Acceptance still required

The unchecked worker and orchestrator gates in `docs/runbooks/acceptance-gates.md` and `TASKS.md` remain unchecked. Use repeated held-out tasks that span at least source/API analysis and software/advisory research, with Daybreak and Qwen results attributed separately. Inspect exact prompts, selected guidance, first useful test time, command effects, context growth, worker handoff reuse, plan changes, independent finding support, report fidelity, operator effort, elapsed time, and model usage. Add interruption/resume and two-slot local-model load cases. A full customer-ready claim also needs enforced or explicitly operationalized scope isolation and an air-gapped end-to-end deployment check.

No code was changed in this audit. The recommended repair order is approval semantics, report/action provenance, then model-call concurrency and evidence handoff efficiency, followed by repeated held-out acceptance. Keep the core fixes generic rather than adding archive- or router-specific branches.
